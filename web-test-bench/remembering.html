ARCHITECTURE SPECIFICATION · FUTURE WORK

Remember selectively.
Forget without confusion.

Node Core OS proposes a requirement-driven memory model: historical information remains available as evidence, but it is not automatically applied to the present. Context forgetting, access restriction, revocation, and data deletion are separate operations.

Explore the model ↓ Read full specification ↗
Transparency note: this page describes proposed future behavior. It does not claim that the complete memory, privacy, or deletion lifecycle is implemented.

01 · CORE PRINCIPLE

The present is the default context

The past remains available as evidence, but a current requirement determines whether relevant history should be recalled and applied.

A · REMEMBER

Recall what is relevant

Select the minimum historical context needed for a specific authorized request. Do not load or disclose an entire personal history by default.

Planned
B · FORGET CONTEXT

Stop applying history by default

A record can remain preserved while being excluded from the active context. Forgetting context does not itself destroy the underlying data.

Planned
C · DELETE

Remove controlled copies

Deletion is a separate operation with explicit scope, authorization, execution results, and limitations. The system must not claim more than it can verify.

Planned
Core distinction: FORGOTTEN ≠ DELETED. PRESERVED ≠ ACTIVELY USED. STORED ≠ AUTHORIZED. AVAILABLE ≠ VALID.

02 · REQUIREMENT-DRIVEN RECALL

From a request to relevant evidence

Memory should be selected by purpose and policy, not by automatically applying every historical record.

01Current requestIdentify the actor, purpose, scope, and requested outcome.
02RequirementDetermine which facts or evidence are actually needed.
03Policy checkCheck authorization, access restrictions, validity, and freshness.
04Selective recallRetrieve only the minimum relevant historical context.
05EvaluationApply that evidence to the current request and report limitations.

03 · TWO STORAGE DOMAINS

Local control and distributed reality

The same lifecycle policy must respect the different guarantees and limitations of each storage domain.

Local storage

The Node can manage local files, registry references, metadata, and controlled keys. A deletion result must state which copies and indexes were actually covered; backups and external copies may remain.

↔

Kubo / IPFS

Removing a reference, unpinning a CID, or deleting the local source does not guarantee that peers or third parties no longer hold the content. A CID does not provide confidentiality or authorization.

Encryption

Private content should not be published in plaintext by default. Destroying a key may prevent decryption by parties without another key copy, but cannot prove that all plaintext copies or backups are gone.

Truthful outcomes

The interface should report exactly what was done: reference removed, local file deleted, content unpinned, key destroyed, or operation incomplete. Never claim “deleted everywhere” without proof.

04 · INDEPENDENT DIMENSIONS

One record can have different states

Storage, active-context inclusion, authorization, validity, and deletion must not be collapsed into one universal status.

ContextApplied, forgotten from active context, or selected for recall
AccessAllowed, restricted, or unavailable to a requester
ValidityCurrent, expired, revoked, or superseded
StorageLocal, distributed, encrypted, or not currently available
RetentionRetained under a defined policy or eligible for deletion
DeletionNot requested, pending, completed within scope, or incomplete
Identity and reputation: a preserved record is not automatically a current identity label. Credentials require their own validity and revocation checks, and reputation should be contextual and based on relevant evidence.

05 · IMPLEMENTATION ROADMAP

Build in verifiable phases

The repository must be audited before runtime changes. Existing storage and content contracts should be reused rather than duplicated.

  1. Audit current modulesReview the local registry, content operations, Kubo lifecycle, identity/evidence models, and tests.
  2. Define schemas and policySeparate context selection, access, validity, retention, revocation, storage, and deletion state.
  3. Test local selective recallProve that a record can be excluded from active context without deleting it.
  4. Add lifecycle operationsImplement restriction, expiry, revocation, and controlled deletion with explicit outcomes.
  5. Integrate Kubo/IPFSTest add/retrieve, references, pin/unpin, publication withdrawal, and failure cases.
  6. Specify encryption and key handlingDefine threat model, backups, recovery, and destructive-operation safeguards first.
  7. Expose real state in the UIShow storage location, access, context state, retention, and deletion scope without overclaiming.
  8. Gate releases on testsCover restart, unavailable storage, stale references, partial failure, and backup/restore scenarios.

This roadmap is a future specification, not a claim that these components or tests already exist.
