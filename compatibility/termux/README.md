# Node Core OS — Termux Lobby

**Status:** experimental; physical-device validation is required.  
**Target:** native Termux on Android, ARM64 first.

## Purpose

The Lobby is the local lifecycle control surface for Node Core OS. It is
installed independently and can run before Node Core OS exists. It is not an
APK. Node Core OS can operate independently after installation.

## One-command Lobby bootstrap

From native Termux, install the minimum bootstrap tools and run:

```bash
pkg update
pkg install curl python tar bash -y
curl -fsSL https://raw.githubusercontent.com/byLAEV/Node-Core-OS/feature/termux-local-lobby/compatibility/termux/bootstrap-lobby.sh -o "$HOME/bootstrap-lobby.sh"
bash "$HOME/bootstrap-lobby.sh"
```

The bootstrap resolves the selected official GitHub branch to a 40-character
commit SHA, downloads that exact source snapshot, rejects unsafe archive paths
and special files, and invokes `compatibility/termux/install-lobby.sh`.
It does not run `pkg upgrade`, use root, or install/update Node Core OS.

The default bootstrap ref is `feature/termux-local-lobby` while this profile is
under review. To select another reviewed ref explicitly:

```bash
NODE_CORE_LOBBY_REF=main bash "$HOME/bootstrap-lobby.sh"
```

The branch ref is resolved at execution time and pinned to a commit for that
download. A stable production installer should be published from a reviewed,
tagged Lobby release after the PR is accepted and physical-device validation
passes.

If the Lobby installer needs OpenSSL CLI, it asks permission to install
Termux's `openssl-tool` package. To approve that package installation
non-interactively:

```bash
bash "$HOME/bootstrap-lobby.sh" --yes
```

## Lobby files and persistent state

Installed application files:

- `~/.node-core/lobby/server.py`
- `~/.node-core/lobby/web/index.html`
- `~/.node-core/lobby/web/manifest.webmanifest`
- `~/.node-core/lobby/web/icon.svg`
- `~/.shortcuts/node-core-lobby`

Persistent service state is kept separately and is not overwritten by Lobby
reinstallation:

- `~/.node-core/lobby/server.json`
- `~/.node-core/lobby/localhost.crt`
- `~/.node-core/lobby/localhost.key`
- `~/.node-core/lobby/lobby.log`
- `~/.node-core/lobby/server.pid`

The installer stages and validates application files, preserves previous files
for rollback, and only commits after the service health check succeeds.

## Local service

The server binds only to `127.0.0.1:8765`. It prefers HTTPS using a local
self-signed certificate generated by OpenSSL. If TLS cannot be enabled, the
server reports and uses HTTP on loopback only.

- HTTPS: `https://127.0.0.1:8765/`
- HTTP fallback: `http://127.0.0.1:8765/`
- Health: `/health`
- Status: `/api/status`
- Diagnostics: `/api/diagnostics`
- Full read-only report: `/api/report`

## Canonical Node Core OS directory manifest

The canonical source is `installer/layout-manifest.json`. It defines the relative directory and file layout rooted at `~/.node-core/`, the component responsible for each directory, persistence rules and invariants. The standard installer reads this manifest to create the runtime directories; the Lobby installer copies the same file to `~/.node-core/lobby/manifests/layout-manifest.json` and exposes it at `GET /api/layout/manifest`. The Lobby home screen includes **Node Core OS Directory Manifest** to display the exact contract.

The manifest is descriptive and versioned; it does not claim that every listed directory already exists. The installer creates the declared directories. The Lobby has its own independently managed subtree and may be installed before Node Core OS. The updater must preserve `storage/`, `ipfs/`, `config.json`, identity and persistent runtime data. The optional systemd user service unit is outside `~/.node-core` as specified in the manifest.

## Generate Report — official TXT / JSON export

The Lobby home screen provides a dedicated **Generate Report** action. It requests a fresh snapshot from the read-only `/api/report` endpoint and presents compatibility checks, Termux/Android environment, Node Core OS detection, tools, installed packages, network/local services, directory structure and privacy limits.

The report can be copied as readable TXT or structured JSON, downloaded as `node-core-termux-report.txt` or `node-core-termux-report.json`, or shared to another Android application through the browser share sheet when supported. If file sharing is unavailable, the Lobby shares the text report; if native sharing is unavailable, it copies TXT to the clipboard.

The JSON is the raw report object returned by the local API. The TXT version is a human-readable rendering of the same snapshot. Both include the UTC generation timestamp and check results. Exporting does not send the report to a remote service. Sharing is initiated only when the user presses **Share report** and selects a destination.

The report is read-only and bounded. It excludes private keys, tokens, credentials and proxy values; it does not read arbitrary file contents or traverse private storage/IPFS contents. This report is a technical inventory, not a security certification.

A self-signed certificate encrypts the local connection but is not automatically
trusted by Android browsers. A browser warning may appear. The `curl -k` option
is for controlled local testing only; it does not establish certificate trust.

## Official package download and SHA-256 staging

The install and update panels now offer an explicit, browser-confirmed
`Download and verify` action when the detected installation state permits it.
The server requires a per-installation random session token, a matching local
Origin and Host, a JSON POST request, and a supported package kind.

The Lobby downloads only the canonical release asset over HTTPS, enforces a
300 MiB maximum and the published byte count, streams SHA-256 over the complete
archive, compares it with GitHub's Release asset digest, then atomically places
the verified file under:

`~/.node-core/lobby/packages/`

Package files and verification receipts are mode 0600; the package directory is
mode 0700. Temporary partial downloads are removed on failure. A receipt
records the release tag, package name, size, expected and actual digest, and
explicitly records that the archive has not been inspected, extracted or
executed.

After staging, the Lobby exposes a separate **EJECUTAR INSTALADOR /
ACTUALIZADOR OFICIAL** action. Before execution the server re-fetches the
current stable-release metadata, requires the staged receipt to match that
exact release and re-hashes the complete archive. It then safely extracts the
package into a private temporary workspace, rejecting absolute paths, parent
traversal, symlinks, special files, excessive file counts and expanded size.
The Lobby executes only the canonical script from that package:
`installer/install.sh` for a new installation or `installer/update.sh` for
an update. No arbitrary command or browser-supplied path is accepted.

Execution is a separate authenticated HTTPS POST after explicit browser
confirmation. The Lobby runs the official script as the unprivileged Termux
user, displays its actual stdout/stderr in an in-page console, and reports
the process exit code, timeout or failure. The official installer initializes
the persistent Ed25519 NODE ID. For a first installation, the Lobby
also requires a declared full name and proof of control of a Bitcoin Mainnet
private key through the local identity form. The accepted HEX scalar is
processed only by the authenticated HTTPS loopback service; the Bitcoin
private key is never written to disk or sent to a remote service.
Python/cryptography memory zeroization is best-effort and cannot be guaranteed.
The name remains self-declared, not civil-identity verified. After
installation, the Lobby verifies possession of the installed Ed25519 NODE ID
key and links the existing Bitcoin entity ID to that node in the local entity
registry. Updates use the official updater and do not request the Bitcoin
private key again. This integration requires green automated CI and
physical-device validation before it can be called production-ready.

## Stable Release discovery in the Lobby

The Lobby exposes a read-only `GET /api/releases/latest` endpoint. It queries
GitHub's canonical latest-release API and validates:

- the release is published, not a draft and not a prerelease;
- the tag is a stable `vMAJOR.MINOR.PATCH` version;
- both official release archives are present;
- each asset has a valid GitHub SHA-256 digest and the exact canonical
  `byLAEV/Node-Core-OS` download URL;
- the SHA-256 values in the release notes match GitHub's asset digest metadata;
- the release page URL is the canonical official GitHub URL.

The install and update dashboard panels show this release information and the
installed version, if detected. If GitHub is unavailable or metadata is invalid,
the Lobby reports that verification is unavailable and does not infer a version.

Release discovery is read-only. Downloading, byte-level SHA-256 verification and
installer execution are separate user-triggered steps described above. Release
metadata alone never authorizes an install or update.

## Node Core OS installation and update boundary

The Lobby installer installs only the Lobby. It is separate from the canonical
Node Core OS installer and updater:

- New installation: the official release's `node-core-os-install-VERSION.tar.gz`
  package and its `installer/install.sh`.
- Existing installation: the official release's
  `node-core-os-update-VERSION.tar.gz` package and its `update.sh`.

The latest stable release must be obtained from GitHub Releases, never inferred
from the repository's development-branch `VERSION` file. The package SHA-256
must match the digest published in that Release before extraction or execution.
The Lobby must detect an existing installation before choosing a path; update
must preserve identity, configuration, local storage and the Kubo/IPFS
repository and must never ask for identity input again.

**Identity boundary:** the Lobby invokes the canonical official package
scripts. The current installer initializes the persistent Ed25519 NODE ID
under \`~/.node-core/identity/\`. The Lobby's first-install identity gate
accepts a declared full name and a Bitcoin Mainnet private-key HEX scalar
(64 hexadecimal characters, valid secp256k1 scalar) through the local browser
form. The local service derives the P2WPKH address and verifies a single-use
ECDSA challenge. The Bitcoin private key is not persisted, logged or sent to a
remote service; it is sent only over the authenticated HTTPS loopback
connection to the local Lobby process. Complete memory zeroization cannot be
guaranteed. After a successful first installation, the Lobby verifies the
installed Ed25519 key's proof of possession and associates the Bitcoin entity
ID with the NODE ID in \`~/.node-core/identity/entity-registry.json\`.
The relationship is recorded as declared, while the cryptographic proof of
NODE ID key possession is verified. A declared name is not civil-identity
verification. Updates preserve both identities and do not ask for the Bitcoin
private key again. No Ethereum private-key or address workflow is implemented
by this milestone.

The Lobby diagnostics API is read-only. It is not an authenticated administrative
API and must not be extended with mutating actions without a separate security
design, explicit authorization, audit logging, rollback and tests.

## Security certificate catalog and Lobby manager

The Lobby includes an independent certificate manager and a bundled canonical
catalog at:

- Installed manager: `~/.node-core/lobby/certificate_manager.py`
- Installed catalog: `~/.node-core/lobby/certificates/catalog.json`
- Runtime inventory: `GET /api/certificates`
- Authenticated local actions: `POST /api/certificates/action`

The catalog separates technical certificates from the eight Node Core OS
security-evaluation/product profiles. The eight profiles are not eight
installable X.509 certificates and are not represented as completed security
guarantees.

### Managed by the Lobby

- Its own loopback TLS certificate and key: inspect, first install, renew,
  repair, local backup and recovery.
- The Node Core OS explicit peer-trust allowlist: inspect, inspect a public
  peer PEM certificate, trust after out-of-band SHA-256 fingerprint
  confirmation, and revoke.
- Public metadata only: issuer/subject, validity, SAN, SHA-256 fingerprint,
  NODE ID and status. Private key contents are never returned or logged.

### Read-only / owned by Node Core OS core or an external PKI

- The Node Core OS P2P identity certificate is validated against the existing
  Ed25519 identity metadata. Lobby never creates, replaces, exports or rotates
  that certificate or its private key.
- Compact JWS identity credentials are a separate project-defined Ed25519
  format, not X.509.
- Public web TLS certificates must be issued by a Web PKI or an explicitly
  managed private CA. The Lobby does not issue public certificates or claim
  that a self-signed certificate is trusted by Android/browser certificate
  stores.

Peer trust changes update the local trust store atomically with mode 0600 and
are effective after the Node Core OS P2P service reloads. Before trusting a
peer, inspect its certificate and verify the exact SHA-256 fingerprint through
an independent channel. Revocation is recorded locally; distributed revocation
synchronization is not claimed by this Lobby milestone.

Lobby TLS changes create protected local backups and require a Lobby restart
to activate the replacement. A recovery operation is offered only when the
backup certificate/key pair passes validation. Android user-CA installation
is not automated: Android/browser trust requires explicit user/platform action.

All mutating endpoints require HTTPS, the local session token and matching
local Origin/Host checks. The manager never touches Node Core OS identity
private keys, local storage contents, or the Kubo/IPFS repository. The Lobby
remains independent and can run before Node Core OS is installed.

The local action audit is stored at
`~/.node-core/lobby/certificates/actions.jsonl`; it contains action names,
timestamps and public fingerprints only.


## 00 · Termux Commands — local command execution

The Lobby includes a **00 · Termux Commands** panel. Select it and press
**REVEAL COMMANDS** to load the available fixed command catalog. Each command
shows its exact invocation and an **EXECUTE** control. Executing a command
opens an in-page terminal window that polls and displays the actual local
Termux process output, exit status and timeout result.

The starter catalog is grouped by environment area and contains only
read-oriented commands:

- **Basic identity:** `pwd`, `whoami`, `id`.
- **Files and directories:** `ls -la` (home directory names and metadata only).
- **System information:** `uname -a`, `date`, `ps -A`.
- **Android information:** `getprop ro.build.version.release` and
  `getprop ro.product.cpu.abi`.
- **Storage:** `df -h`.
- **Termux packages:** `pkg --version` and `pkg list-installed`.
- **Runtime:** the Lobby's Python interpreter with `--version`.

The catalog labels each command with a short explanation and groups it in the
Lobby by category. Process and package listings may be truncated at the output
limit. Commands such as `pkg install`, `apt upgrade`, `rm`, `chmod`,
`mv`, `cp`, `termux-setup-storage` and `su` are intentionally excluded
from this introductory read-only catalog.

Security boundary:

- The browser submits a fixed command identifier, never a command string.
- The server maps identifiers to a reviewed allowlist and starts processes
  with argument arrays and `shell=False`; no shell command injection path is
  provided.
- Mutating execution endpoints require the local session token, matching
  loopback Origin/Host and HTTPS. HTTP fallback can show the read-only catalog
  but cannot start or retrieve command sessions.
- No root, arbitrary command input, interactive shell, stdin forwarding or
  command chaining is provided in this first milestone.
- Each command has a 30-second timeout and a 64 KiB output cap; at most two
  commands may run concurrently. Output and sessions are held in memory only.
- Opening the panel does not execute anything. A user must press EXECUTE for
  each command.

This is a controlled command runner, not a full interactive Termux terminal.
A later milestone may add explicitly reviewed interactive terminal features,
but must preserve loopback-only access and explicit execution authorization.

## Android home-screen entry

The installed Termux:Widget script is `~/.shortcuts/node-core-lobby`.
Termux:Widget can start Termux and then open the local URL. A PWA icon alone
cannot restart Termux after Android has stopped its process. Android battery
management may stop background processes; persistent execution is not guaranteed.

## Diagnostics and privacy

The report is read-only. It does not read arbitrary file contents, run shell
startup files, install/remove packages, change permissions or alter network
settings. It excludes SSH/GnuPG, keys, private credentials, wallets, identity
material, caches and Git internals. Symlinks are not followed. Storage and IPFS
directory contents are not traversed. Proxy presence may be reported, but proxy
values are never exposed. Package and directory output are bounded.

## Bitcoin identity and NODE ID association

The first-install flow is available from the Lobby identity panel. Enter only
the declared name and Bitcoin HEX private key on the local device; never paste
the private key into ChatGPT, issue trackers, CI logs, screenshots, or support
messages. The browser sends the key only to the authenticated HTTPS loopback
service. The local service derives the Mainnet P2WPKH address, verifies the
one-time challenge, and persists only public proof material.

After the first installation finishes, use **ASSOCIATE WITH INSTALLED NODE
ID** if the association did not complete automatically. The service loads the
installed Ed25519 identity, verifies a fresh or previously staged possession
proof, and idempotently updates the local entity registry. A retry reuses the
same staged proof, so a process interruption does not require the Bitcoin key
to be entered again. The Ed25519 private key belongs to Node Core OS and is
stored separately in its protected identity directory; it is not the Bitcoin
private key.

The registry relationship is \`declared\`; proof of possession of the Ed25519
NODE ID is cryptographically verified. Neither result establishes a person's
civil identity.

## Manual verification

```bash
command -v openssl
openssl version
curl -kfsS https://127.0.0.1:8765/health
curl -fsS http://127.0.0.1:8765/health
cat "$HOME/.node-core/lobby/server.json"
tail -n 50 "$HOME/.node-core/lobby/lobby.log"
ps -A | grep '[s]erver.py'
```

A successful health response reports the actual transport as either `https`
or `http`. Do not mark HTTPS validated unless the response says
`"transport": "https"` and the HTTPS API endpoints also respond.
